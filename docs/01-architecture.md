# XBASIC 6.2.3 — System Architecture

This chapter describes how XBASIC 6.2.3 is put together: the language's
module model, the compilation pipeline, the runtime/executable model, and the
internal conventions that tie the self-hosted sources together.

## 1. The XBASIC Program Model

An XBASIC source file (`.x`) is a sequence of sections. The standard layout,
documented in `templates/prolog.xxx` and enforced by the PDE, is:

```
' 1. PROGRAM "progname"            - 1-8 char program/file name (no extension)
' 2. VERSION "0.0000"              - version string, bumped before saving
' 3. IMPORT "libname"              - pull in a .dec declaration file / library
' 4. TYPE <typename> ... END TYPE  - composite data types (also UNION)
' 5. DECLARE FUNCTION ...          - internal function prototypes
' 6. EXTERNAL FUNCTION ...         - functions provided by other modules
' 7. $$ConstantName = value        - shared constants (the $$ prefix)
' 8. SHARED variable               - shared variables
'
' then executable code:
'   FUNCTION Entry() ... END FUNCTION   - execution starts here
'   FUNCTION Other() ... END FUNCTION   - all other functions
```

The `template/entry.xxx` comment summarizes: *"Programs contain: 1. A PROLOG
with type/function/constant declarations. 2. This Entry() function where
execution begins. 3. Zero or more additional functions."* `END PROGRAM` is
optional after the last function.

## 2. The Module System

XBASIC has a genuine module/unit system expressed as program-level
statements:

| Statement | Meaning |
|---|---|
| `PROGRAM "name"` | Names the module (also queried at runtime via `PROGRAM$()`) |
| `VERSION "n"` | Module version (queried via `VERSION$()`) |
| `IMPORT "name"` | Loads `name.dec` — the declaration file for a library or OS DLL (e.g. `IMPORT "xst"`, `IMPORT "kernel32"`) |
| `EXPORT` ... `END EXPORT` | Lists the functions/constants a *library* exposes to importers (see `xut.x`) |
| `DECLARE FUNCTION f(args)` | Prototype of a function defined in this file |
| `INTERNAL FUNCTION` | Function with internal (file-local) scope |
| `EXTERNAL FUNCTION` | Function supplied by another module (e.g. `XxxStartApplication` in the user program) |
| `CFUNCTION` | A function callable from C or invoked by the runtime (C calling convention); used for signal/exception handlers |
| `LIBRARY` / `LIBRARY(0)` | Compiles the file as a function library; `LIBRARY(0)` returns true at runtime if the current module was compiled as a library |

### Library initialization protocol

Libraries expose an `Init` entry point that is called by the runtime in a
fixed order. In `src/linux/xrun.x` (and identically in `win32/xrun.x`):

```basic
IFZ firstEntry THEN
    firstEntry = $$TRUE
    ##XBSystem = $$XBSysLinux        ' <- runtime OS identification
    InitProgram ()
    Xst ()                           ' standard library init
    XutInit ()
    Xio ()                           ' I/O layer
    Xin ()                           ' sockets/network
    Xma ()                           ' math
    Xcm ()                           ' complex
    Xgr ()                           ' graphics
    Xui ()                           ' GuiDesigner toolkit
END IF
```

Each library's `Xxx()` init registers its functions with the runtime so
importers can resolve them.

### Linkage glue between modules

Libraries may need services of the *host* (the PDE or the standalone
runtime). The convention is that the host provides `Xxx*` / `Xit*` functions
and the library declares them. `xrun.x` shows the contract explicitly — it
declares empty placeholder implementations with comments like:

```basic
DECLARE FUNCTION XitGetDECLARE (func$, declare$)  ' called by xui.x
...
' These empty functions need to be in here because they're
' called by xst.x and/or xui.x
```

and one *real* one:

```basic
FUNCTION XitSoftBreak ()
    pid = getpid ()
    kill (pid, $$ExceptionBreakKey)   ' Linux
END FUNCTION
```
```basic
FUNCTION XitSoftBreak ()
    RaiseException ($$EXCEPTION_CONTROL_C_EXIT, 0, 0, 0)   ' Win32
END FUNCTION
```

So the same host-services contract is implemented per platform with entirely
different OS calls.

## 3. Compilation Pipeline

The compiler is invoked as `xb <file>.x` (and `xb <file>.x -lib` to compile a
library). It is a **source-to-assembly compiler**:

```
      xb prog.x
prog.x ──────────► prog.s      (i486 assembly, generated by xcol.x / xcow.x)
                        │ gcc -c  (Linux)   or  spasm  (Win32)
                        ▼
                      prog.o
                        │ link
                        ▼
               executable / library
```

Key evidence from `src/Makefile`:

```make
%.s: %.x
	xb $< -lib          # every .x library is compiled by the installed xb

# Linux
bin/xb: $(XBOBJS) bin/libxb.a
	$(CC) $(CFLAGS) $(XBOBJS) -rdynamic -L/usr/X11R6/lib -lX11 -lm -ldl -o bin/xb

# Win32
bin/xb.exe: $(XBOBJS) xb.rbj bin/xb.lib
	$(LD) $(LDFLAGS) -out:bin/xb.exe $^ $(LIBS)   # kernel32 user32 gdi32 wsock32 msvcrt
```

The compiler emits native i386 assembly; there is no bytecode interpreter and
no VM. Compiled XBASIC *is* native code. The `xdis.x` disassembler exists
because the debugger needs to reverse the emitted assembly back to readable
form (see [`04-libraries.md`](./04-libraries.md)).

### Generated-code symbol surface

The Windows export file `src/win32/xb.def` (1,187 lines) reveals the runtime
symbols the compiler's generated code calls. The mangling is highly
descriptive:

- `%_concat.string.a0.eq.a0.plus.a1.ss` — string concatenation helper
  (source/target operand kinds encoded in the suffix).
- `%_DimArray`, `%_RedimArray`, `%_FreeArray`, `%_assignComposite` — array
  and composite-type operations.
- `XxxFABS`, `XxxFSIN`, `XxxFPREM`, ... — wrappers around every x87 FPU
  instruction, so floating point is controlled at runtime.
- `%_eeeAllocation`, `%_eeeOverflow`, `%_eeeErrorNT`, `%_OutOfBounds`,
  `%_NeedNullNode`, `%_UnexpectedLowestDim` — runtime error entry points.
- `malloc`/`realloc`/`free`/`calloc` exported under many alias spellings
  (`_malloc`, `__malloc`, `Xmalloc`, `%____malloc`, ...) — the runtime
  redirects all heap allocation through its own memory manager.

This shows the ABI contract between the compiler's code generator and the
assembly/C runtime library (`xlib.s`, `xzzz.s`, `xbiface.c`).

## 4. The Memory Model

`src/linux/chkmem.c` documents the heap design:

> "The XBasic dynamic memory ('heap') is a linked list, beginning with
> `__DYNO` and ending with `__DYNOX`."

Each block carries a 4-word header (`TMemBlock`):

```c
struct TMemBlock {
    unsigned long lAddrUp;    /* distance in bytes to next block; 0 for last */
    unsigned long lAddrDown;  /* back pointer */
    unsigned long lSizeUp;    /* size accounting */
    unsigned long lSizeDown;
};
```

`__DYNO` and `__DYNOX` are symbols defined in the assembly startup files
(`xlib.s`), anchoring the heap between them. `xb_checkmem()` walks the chain
and verifies it ends exactly on `__DYNOX`. The runtime redirects all of
`malloc/realloc/free/calloc` (see `xb.def` aliases) through this allocator so
that XBASIC strings, arrays, and composite values are managed uniformly.

The README documents two heap-related compiler conventions:

- **`##WHOMASK`** — *"self-implements a crude 'two-thread' scheme that
  distinguishes memory allocated for the development environment from
  programs running in it."* This is how the PDE and a program being
  debugged/run can coexist without clobbering each other's allocations.
- **`##LOCKOUT`** — *"prevents signal being processed inside signals where
  that might cause problems"* (re-entrancy guard for exception handling).

## 5. The Exception Model

Exceptions are a first-class, user-extensible mechanism. The runtime
(`xrun.x`) is the dispatcher:

- On Linux, `EstablishSignals()` installs one C handler
  (`XxxXitMain` via `xb_sigaction`) for SIGINT, SIGQUIT, SIGILL, SIGTRAP,
  SIGABRT, SIGFPE, SIGBUS, SIGSEGV, SIGALRM, SIGTERM, SIGVTALRM, blocking all
  other signals inside the handler (`sig.sa_mask = mask`).
- On Win32, the equivalent path uses structured exceptions
  (`RaiseException`/`XitMain (sigNumber, sigSource)`) and returns
  `$$EXCEPTION_CONTINUE_EXECUTION` / `$$EXCEPTION_CONTINUE_SEARCH`.

The flow, identical in spirit on both platforms:

```
OS signal/exception
   │
   ▼
XxxXitMain / XitMain (sigNumber)
   │
   ├─ sigNumber == 0  → first entry: EstablishSignals(); XxxStartApplication()
   │
   └─ otherwise:
        XstSystemExceptionToException (sigNumber, @exception)   # map OS → XBASIC
        SELECT CASE exception
            CASE $$ExceptionTimer: XxxXstTimer($$TimerExpire,...) ; return
        END SELECT
        XstExceptionNumberToName (exception, @exception$)
        XstGetExceptionFunction (@response)      # user-installed handler, or
        XxxSetExceptions (exception, sigNumber)  #   a default action
        DO
            SELECT CASE response
                CASE $$ExceptionContinue  : RETURN false
                CASE $$ExceptionTerminate : RETURN true
                CASE ELSE                 : func = response   # call user handler
                                           : response = @func()
            END SELECT
        LOOP
```

User programs therefore get a hook: an **exception function address** is
queried (`XstGetExceptionFunction`), and if non-standard the runtime calls
it — inside the signal context — and honors its `Continue`/`Terminate`
verdict. This is how a BASIC-level `ON ERROR`-style mechanism works while the
actual trapping is native signals/SEH.

## 6. Compiler-Directive and Constant Conventions

Two `#`-prefixed notations appear throughout every source file. They are the
key to reading XBASIC sources:

| Notation | Meaning | Examples |
|---|---|---|
| `##NAME` | Compiler/global **directive or runtime system variable** (preprocessed at compile time, or a runtime global) | `##XBSystem`, `##INEXIT`, `##APP`, `##ENTERED`, `##WHOMASK`, `##LOCKOUT`, `##XBDir$`, `##CODE`, `##EXCEPTION`, `##OSEXCEPTION`, `##XERROR` |
| `$$NAME` | **Constant** (shared constant, usually defined in the PROLOG or an imported library) | `$$TRUE`, `$$FALSE`, `$$XBSysLinux=1`, `$$XBSysWin32=2`, `$$TimerStart`, `$$ExceptionContinue`, `$$LOGE10`, `$$MAX_ULONG`, `$$PathSlash$` |

The `$$XBSys*` constants and the `##XBSystem` variable are *the* runtime
platform switch: XBASIC code branches on it (see `xutpde.x` below). Whether
the compiler supports `##IFDEF`-style conditional *compilation* is covered in
[`06-cross-platform.md`](./06-cross-platform.md).

## 7. Runtime Platform Identification

`src/shared/xut.x` exports the platform switch to every module:

```basic
EXPORT
    $$XBSysLinux = 1
    $$XBSysWin32 = 2
    EXPORT XBSystem
    DECLARE FUNCTION XutInit()
END EXPORT
```

The runtime sets it at startup (`##XBSystem = $$XBSysLinux` / `$$XBSysWin32`)
before any library initializes. `xutpde.x` then uses it for OS-dependent
defaults — the canonical example of runtime branching:

```basic
IF ##XBSystem == $$XBSysWin32 THEN
    ##XBDir$ = "c:\\xb"
ELSE
    ##XBDir$ = "/usr/xb"
END IF
```

`XBDir$` itself is resolved in priority order: environment variable `XBDIR`
→ derived from the executable's own pathname → platform default. This is
what makes the installation location arbitrary (since 6.1.0).

## 8. Runtime / Executable Architectures

There are **two ways to run XBASIC code**, and the two platforms realize them
differently:

### 8.1 Inside the PDE (development mode)

- **Linux**: one process. `bin/xb` contains the PDE (`xit.x`), the compiler
  (`xcol.x`), the disassembler (`xdis.x`), and all libraries linked together.
  `##WHOMASK` separates PDE memory from program memory in the shared heap.
- **Win32**: `xb.exe` is a thin native launcher; the brains live in
  **`xb.dll`** (PDE runtime) which contains the IDE, compiler, and libraries.
  User programs compiled in the PDE run against the same `xb.dll`.

### 8.2 Standalone executables (production mode)

- **Linux**: `libxb.a` is a **static** library. A program `prog.x` is
  compiled to `prog.o` and linked with `appstart.o + prog.o + libxb.a` into a
  native executable:
  ```make
  $(APP): $(APP).mak $(APP).x $(APP).o
      $(CC) $(CFLAGS) $(APP).o $(LIBS) -rdynamic $(STDLIBS) -o $(APP)
  STDLIBS = -L/usr/X11R6/lib -lxb -lX11 -ldl
  ```
  `xrun.o` (from `xrun.x`) provides the runtime entry.
- **Win32**: standalone programs link `xstart.o + prog.o + xb.lib` and run
  against **`xbrun.dll`** — a copy of the runtime *without* the IDE/compiler.
  `README.Win32` explains the swap: *"copy it and rename that copy to
  `xb.dll` ... Make sure that that copy is found before the standard xb.dll
  is found (e.g. by putting it in the current directory). If you don't do
  this then your standalone program will start the PDE."*

The runtime entry point is `XxxXit`/`Xit` in `xrun.x`; the OS-level entry is
in the assembly startup (`xstart.s`), which pushes
`argc/argv/envp` + `&WinMain` + `%_StartApplication` and calls `XxxMain` in
the runtime library (see [`06-cross-platform.md`](./06-cross-platform.md) for
the exact stack handoff).

## 9. Cross-Platform Source Strategy (summary)

The architecture achieves source compatibility with a **layered split**:

1. **Shared code** (`src/shared/`) — platform-independent libraries
   (`xui.x`, `xma.x`, `xcm.x`, `xdis.x`, `xut.x`, `xutpde.x`).
2. **Per-platform twins** (`src/linux/`, `src/win32/`) — same *interface*,
   different *backend*: `xcol.x`/`xcow.x`, `xit.x`, `xst.x`, `xgr.x`, `xin.x`,
   `xrun.x`. A user program imports a fixed set of names and never sees
   which platform it runs on.
3. **Foreign-function declarations** (`include/*.dec`) — XBASIC reaches the
   OS through declared imports (`kernel32`, `user32`, `gdi32`, `wsock32`,
   `shell32`, `winmm`, `xlib`, `xwin`, `elf32`, `clib`), so the same `IMPORT`
   statement works for Win32 DLLs and Linux shared libraries.
4. **A thin native shim** — `xbiface.c` (Linux C glue), `xexcept.obj`
   (Win32 SEH), and i386 assembly startup per platform.
5. **Runtime OS switch** — `##XBSystem` for the few truly divergent paths.

Chapter [`06-cross-platform.md`](./06-cross-platform.md) details each layer.
